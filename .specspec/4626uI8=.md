# Parse a chain of editing steps into one final candidate before anything is written

Only the top-level commands `add`, `update` and `delete` can be repeated and combined as steps of one invocation, and each step takes its ordinary arguments and options. A bare `add`, `update` or `delete` starts a new step. The value of an option is literal even when it equals the name of a command, and so are both values of `--replace`. Every step is parsed before standard input is read or a node file is written. An invocation is rejected as a whole, with no edit carried out in part, when it mixes in a reading command, `init`, `recover` or `api`, when it has an unknown or surplus argument, or when an option of a step is malformed.

`add --as NAME` gives a new node a local name that is valid within the invocation: one letter followed by up to 63 letters, digits, underscores or hyphens. A parent written as `$NAME` resolves to the generated ID of that node, also when the step that defines the name comes later. The complete invocation describes one final candidate, and its steps take effect together or not at all. Each node is edited by one step, and a new node receives all its fields in its `add` step. A name that is defined twice, a name that no step defines and conflicting or repeated edits of one node are rejected. A local name is stored in no node file, ends with the invocation and reserves no ID in a dry run.

`--dry-run`, `--require-valid`, `--yes` and `--json` can stand on any step and apply to the whole invocation. A dry run writes no node file. `--require-valid` checks the complete final candidate, in whatever order the steps stand and whether or not the graph was valid before. The deletions of all steps are assessed together and need one consent, under the writer lock, and they delete exactly the selected files with the usual warnings, the check of original bytes and the recovery. The receipt reports the IDs generated for local names, the changed paths, the validity and the affected scope.

An invocation of one step behaves as the single command does, with the arguments, the standard input and the response that the graph editors rely on. A step without messages takes its body from standard input within the size limit, and nonempty input needs exactly one step that can take it. A step that names more than one source for its body is rejected before anything is written. The hidden options `--parents-json` and `--sources` serve integrations. A reviewed deletion plan belongs to one `delete` that stands alone, and a chain that contains one is rejected. `add`, `update` and `delete` with their options for fields are the whole public way to edit, for a single node and for a composed change alike.

A chain has at most 1024 steps. Its arguments are limited to 16 MiB, and so is the text that it supplies for bodies and for both sides of replacements. These limits apply on top of the limit for each node and of the smaller limits of an operating system.
