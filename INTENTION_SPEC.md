Here my idea for both a concept for new agentic spec "aware" (i do not want to call it driven) development and a tool to make use of it. This file serves as a living documentation and specification until the tool/framework that is developed here can overtake its own specification and documentation.

# Concept: Intention-Conclusion Specification Spectrum Directed Acyclic Graph (dag, or specspecdag)
The core idea is that a specification lives on a spectrum between intention and conclusion. With AI/agentic coding this is further complicated because details of a specification are often worked out in a tandem manner together with an AI. Signing off on details of a specification proposed by an AI can accidentally lump together potentially suboptimal conclusions with the actual core intention. To explore different solutions, architectures, UIs, etc. for a well defined problem or task the engineer needs to have a way of communicating these things to an AI agent in a flexible specification that lives on exactly that spectrum of intentions all the potential/proposed conclusions to explore.

In the specspecdag (intention-conclusion specification spectrum directed acyclic graph) nodes are minimal coherent specification elements (requirements) linked by directed intent-conslusion dependency. Requirements close to or at the source level are less flexible core intentions, requirements close to or at the sink level are conclusions. There should only be one single manifesto root source node which holds the core idea summary of the project. Implementation nodes are final sinks that can hold source level implementation explanations, bascially code comments on steroids from the perspective of the specification. In between only exist requirement nodes, each must be a child of (or must depend on) one or more manifesto or requirement nodes. If a node has more than one parent, the level of these parents (their distance to the manifesto node) can be different or the same. (Note that my description of source/sink, parent/child and intent/conclusion implies that the directionality is parent -> child; This is up to discussion.) The intention/conclusion spectrum position is never explicitly documented, it is a result of the requirement's relative position in the graph.

Note that this concept deliberately has no opinions about things like functional vs non-functional requirements, architectural, framework or programming language choices. It is left to the user what he intents and even things like programming languages can be fixed as intentions for arbitrary reasons, sometimes even outside the influence of the user.

# Git+Tool Managed Directory of SpecDAG Node Markdown Files
The canonical project root level _specspec directly and only holds the node files. Each markdown file with yaml frontmatter is one node in the graph. The file name is exactly the full node identifier followed by .md, ending with =.md. The yaml frontmatter holds the type (manifesto/requirement/implementation) and the graph position/dependencies identified via the identifier. The main markdown contains the binding text with little headlines and structure. It has to be discussed if enumerations are allowed/sensible or should rather become children itself. The manifest node can hold global meta info like a spec format version.

The files are not meant to be manually changed, instead a pipx-able/uvx-able python commandline tool manages all changed to the specification spectrum graph. The tool also offers a git hook to check the consistency and shield against corrupting manual edits.

A visual studio code extension displays the graph and allows visually guided editing. This is the recommended way for the user to edit the specification spectrum graph. The visual studio visual specification spectrum graph editor also works together with visual studios git integration. One can see deltas between workspace and last commit or visualize graphical diffs between different commits.
